Anomalies & Redundancy
Core idea: Poorly designed tables cause redundancy, which leads to anomalies. Normalization fixes this by splitting tables intelligently.
Redundancy
Data Redundancy
Same data stored in two or more places. Wastes space and causes inconsistency.

Row-level: Same row repeated (fix: add primary key).
Column-level: Columns repeat data across rows — leads to all three anomalies below.
Insertion Anomaly
Can't insert without related data
A child cannot be inserted without the parent existing first.

Example: Adding a student with dept_id = 6 fails because dept 6 doesn't exist yet.

Definition: The inability to add data due to absence of other data.
Updation Anomaly
Update in one place, missed elsewhere
Duplicated data updated in one row but not in all copies.

Example: English dept changes to Dept_ID 8, but the Student table still shows the old ID.
Deletion Anomaly
Deleting causes unintended data loss
Deleting one record accidentally removes other important information.

Example: Deleting the "Computer Science" department also deletes all CS student records.
Memory trick: Insert can't happen · Update only in one place · Delete removes too much → I.U.D
Functional Dependency
Key idea: X → Y means "knowing X, you always know Y." X is the determinant (LHS), Y is the dependent (RHS).
Definition
Functional Dependency X → Y
The value of X uniquely determines the value of Y. If two rows have the same X, they must have the same Y.

Valid: Ssn → Ename (one SSN → one employee name)
Valid: {Ssn, Pnumber} → Hours
Valid: dept_name → dept_building
Armstrong's Axioms (1974)
3 Core Inference Rules
1. Reflexivity: If Y ⊆ X, then X → Y
  e.g. {roll, name} → name ✓

2. Augmentation: If X→Y then XZ→YZ
  e.g. roll→dept then {roll,name}→{dept,name} ✓

3. Transitivity: If X→Y and Y→Z, then X→Z
  e.g. roll→dept, dept→building → roll→building ✓
Types of Functional Dependencies
Trivial FD
Y is a subset of X
{roll, name} → name (trivial — name is already part of the left side).
Also: roll → roll.

These are always true and "obvious."
Non-Trivial FD
Y is NOT a subset of X
roll → name (non-trivial — name is not part of roll).
{roll, name} → age (also non-trivial).

These are the meaningful, useful ones.
Multivalued FD
Dependents don't depend on each other
roll → {name, age} is multivalued because name and age are independent (name→age doesn't hold, age→name doesn't hold).
Transitive FD
Indirect dependency via a third attribute
If enrol→dept and dept→building, then enrol→building is transitive (indirect, through dept).

This is what 3NF eliminates!
Invalid FD Test: If two rows have the same LHS value but different RHS values → the FD is INVALID.
Example: "xyz" appears as both CS and IT student → name→dept is invalid.
Normal Forms
Goal: Each higher normal form eliminates one more type of problem. You must satisfy all lower NFs first. Invented by Edgar Codd (1NF–3NF), and extended with Boyce to create BCNF.
Normal FormRule / ConditionWhat it eliminatesHow to fix
1NF All values must be atomic (single, indivisible). No multi-valued attributes. Primary key must exist. Multi-valued columns (e.g., multiple movies in one cell) Separate multi-valued attrs into new table OR expand rows OR create separate columns
2NF Must be in 1NF. Every non-prime attribute must be fully functionally dependent on the entire primary key. Partial dependency — non-key attr depends on only part of a composite key Split: move partially dependent attr + its determinant into a new table
3NF Must be in 2NF. No transitive dependency. NPA→NPA not allowed. (For every FD X→Y: X is superkey OR Y is prime attr) Transitive dependency — non-prime depends on another non-prime If X→Y is transitive: R1 = (X, X⁺) and R2 = (R − Y⁺)
BCNF Must be in 3NF. For every FD X→Y, X must be a superkey. No exceptions, even for prime attrs. Cases where a non-superkey determines a prime attribute Decompose table so the LHS of every FD becomes a superkey
Quick Test for Each Level
  • 1NF: Any column with multiple values? Atomic? Primary key exists? → Fix if not.
  • 2NF: Does any non-key column depend on only PART of a composite key? → Partial dependency = fix.
  • 3NF: Does a non-key column depend on ANOTHER non-key column? → Transitive = fix.
  • BCNF: Is the left side of EVERY FD a superkey? If not → fix.
3NF Decomposition Rule: If game→feestructure is transitive (NPA→NPA):
R1 = (game, feestructure) and R2 = (rollno, game)
BCNF Example: Student-Professor: professor→subject, but professor is not a superkey.
Fix: Split into Student(student_id, professor) and Professor(professor, subject).
Transaction Processing
A transaction is an atomic unit of work — either ALL operations succeed (commit) or NONE of them do (rollback). Boundaries: begin_transaction … end_transaction.
Low-level Operations
Inside a transaction
begin_transaction — marks the start
read_item(X) — read X from DB to memory buffer
modify_item(X) — change X in memory
write_item(X) — write X from memory back to DB
commit — permanently save all changes
rollback — undo all changes since begin
Transaction States
Life cycle of a transaction
1. Active — executing READ/WRITE ops
2. Partially committed — all operations done, not yet confirmed
3. Committed — permanently recorded in DB
4. Failed — error or abort detected
5. Aborted — rolled back, DB restored to before
6. Terminated — left the system
⚠ Concurrency Problems — 4-mark Essay Topic
When multiple transactions run concurrently without control, 4 problems can occur:
1. Lost Update
One write overwrites another
T1 reads X=100, T2 reads X=100.
T1 deducts 50 → writes X=50.
T2 adds 10 → writes X=110 (based on old read of 100).

T1's update is LOST. Correct value should be 60.
2. Dirty Read
Read uncommitted/invalid data
T1 writes X=50 (from 100). Not committed yet.
T2 reads X=50 and uses it.
T1 FAILS and rolls back → X=100 again.

T2 worked with a value that never really existed.
3. Incorrect Summary
Aggregate reads mix old and new
T2 computes SUM of all records while T1 is updating them.
Some values read before update, some after.

The aggregate result is wrong — a mix of old and new values.
4. Unrepeatable Read
Same read returns different values
T2 reads X=100.
T1 updates X to 200.
T2 reads X again and gets 200.

Same transaction, same item, two different values — unrepeatable.
Why Recovery is Needed (3-mark question)
System crash
Hardware, software, or network error during execution.
Transaction error
Integer overflow, division by zero, wrong parameter values, logical errors.
Local errors
Insufficient account balance or other business rule violation triggers cancel.
Disk failure
Head crash or malfunction causes data loss during read/write.
Catastrophe
Power failure, fire, theft, wrong tape, sabotage, accidental overwrite.
ACID Properties
ACID properties ensure database integrity during transaction processing. These 4 properties together guarantee reliable transactions.
A — Atomicity
"All or Nothing"
Either the ENTIRE transaction executes or NONE of it does.
No partial execution allowed.

Example: Transfer ₹100 from X to Y.
If debit from X succeeds but credit to Y fails → entire transaction is rolled back.

Two operations: Abort (changes not visible) and Commit (changes visible).
C — Consistency
Database stays valid before and after
Integrity constraints must hold before AND after every transaction.

Example: Money transfer:
Before: 500 + 200 = 700
After: 400 + 300 = 700

Total is preserved → consistent! If T1 completes but T2 fails → inconsistent.
I — Isolation
Transactions don't interfere with each other
Each transaction runs as if it is the only one in the system.
Intermediate results are hidden from other transactions.

Multiple transactions may run concurrently, but each must be unaware of others.

Achieved using locks or concurrency control protocols.
D — Durability
Committed = permanent, even after crash
Once committed, changes survive even if the system crashes or restarts.

If the system fails after commit but before writing to disk → data is recovered when the system restarts.

Achieved using: mirrored disks, backup operations, and log files.
Memory trick: All or nothing · Correct always · Isolated completely · Durable forever → ACID
Schedules & Serializability
Schedule: An ordering of operations from n transactions. Goal: produce the same result as some serial execution (even if operations are interleaved).
Serial Schedule
One transaction at a time
T1 completes fully, then T2 starts. No interleaving. Always produces correct result. But slow — no parallelism.
Non-Serial Schedule
Operations interleaved
Operations from different transactions mixed. Faster. May or may not be correct — need to test for serializability.
Serializable Schedule
Non-serial but produces serial result
A non-serial schedule that produces the same result as some serial schedule. Two types: Conflict Serializable and View Serializable.
Conflict Serializability — Precedence Graph Method
Two operations CONFLICT if all 3 conditions hold:
1. They belong to different transactions
2. They access the same data item
3. At least one is a WRITE

Conflict pairs: R-W, W-R, W-W on same item.  (R-R is NEVER a conflict)
Algorithm — Precedence Graph
  • Create one node per transaction in the schedule.
  • If Ti writes X, then Tj reads X → draw edge Ti → Tj
  • If Ti reads X, then Tj writes X → draw edge Ti → Tj
  • If Ti writes X, then Tj writes X → draw edge Ti → Tj
  • If the graph has NO CYCLE → schedule is Conflict Serializable ✓
    If there IS a cycle → NOT conflict serializable.
  • Serialized order = Topological Sort (process nodes with indegree 0 first).
View Serializability — 3 Conditions
1. Initial Read
If Ti reads X first in S1, then Ti must also read X first in S2.
2. Updated Read
If Ti reads X that was written by Tj in S1, then Ti must also read X written by Tj in S2.
3. Final Write
If Ti does the last write on X in S1, then Ti must also do the last write on X in S2.
Recoverability Types
Recoverable
Tj commits after Ti (if Tj read Ti's write)
If T2 reads data written by T1, T1 must commit before T2 commits.
Irrecoverable
Tj commits before Ti — VERY BAD
T2 reads T1's uncommitted data and commits. T1 then fails. T2 can't be undone. System is in an unrecoverable state.
Cascading Rollback
One failure = chain of rollbacks
T10 fails → T11 (read T10's data) must rollback → T12 (read T11's data) must rollback. Single failure causes cascading effect.
Cascadeless
Only read COMMITTED data
Tj reads X only after Ti (who wrote X) has committed. Ti's commit appears before Tj's read. No cascading rollbacks possible.
Strict Schedule
Cannot read OR write until writer commits
No transaction can read or write X until the last transaction that wrote X has committed or aborted. Strictest form.
Locking & Two-Phase Locking
Locking protocols are concurrency control mechanisms. A Lock Manager handles lock requests via message passing between transactions.
Shared Lock (S)
Read-only lock
Multiple transactions can hold an S-lock on the same item simultaneously.

Used for READ operations. Cannot modify data while holding S-lock.
Requested with: lock-S(X)
Exclusive Lock (X)
Read + Write lock
Only ONE transaction can hold X-lock. No other lock (S or X) allowed on same item simultaneously.

Used for WRITE operations.
Requested with: lock-X(X)
Lock Compatibility Matrix
Request →
S (Shared)
X (Exclusive)
S (Shared)
✓ Compatible
✗ Not compatible
X (Exclusive)
✗ Not compatible
✗ Not compatible
Only S-S is compatible. Everything involving X is incompatible.
Two-Phase Locking (2PL)
Rule: Once a transaction releases ANY lock, it cannot acquire NEW locks. There are exactly two phases.
Phase 1: Growing
Acquire all locks needed
Transaction can acquire locks. Cannot release any. The point where ALL needed locks are held = Lock Point. After lock point → shrinking phase begins.
Phase 2: Shrinking
Release locks — NO new locks!
After first unlock, no new locks can be acquired. Only releasing from here until transaction ends.

YOU CANNOT ACQUIRE A LOCK AFTER UNLOCK in 2PL.
Variants of 2PL
TypeRuleAdvantage
Basic 2PLStandard growing + shrinking phasesEnsures serializability
Strict 2PLMust satisfy 2PL + hold all X-locks until commit/abortRecoverable + Cascadeless
Rigorous 2PLMust satisfy 2PL + hold ALL locks (S + X) until commit/abortRecoverable + Cascadeless + easier to implement
Disadvantages of 2PL
Irrecoverable
Basic 2PL can produce irrecoverable schedules — Strict/Rigorous 2PL fix this.
Deadlock
T1 waits for T2's lock, T2 waits for T1's lock → neither can proceed. Circular wait = deadlock.
Cascading Rollback
Basic 2PL allows dirty reads → cascading rollbacks possible. Strict/Rigorous 2PL prevent this.
Log-Based Recovery
The System Log is a sequential, append-only file on stable storage. It records ALL transaction operations. Written BEFORE any DB modification. Cannot be corrupted by ordinary failures.
Log Entry Types
[start_transaction, T] → T has started execution [read_item, T, X] → T read item X [write_item, T, X, old, new] → T changed X from old_value to new_value [commit, T] → T completed successfully — changes permanent [abort, T] → T was aborted
Commit Point
Commit point = moment when ALL operations are done AND their effects are recorded in the log.
Then [commit, T] is written into the log.

Force Writing: Before committing, any log data not yet on disk MUST be written to disk first (to survive a crash right after commit).
Recovery Techniques
Deferred DB Modification
Write to DB only AFTER commit
Log everything first. DB is NOT touched until commit.

On failure before commit → just ignore the log entries. Nothing to undo.

REDO committed transactions on recovery.
Immediate DB Modification
Write to DB DURING execution
DB updated as operations happen (before commit).

On failure → UNDO uncommitted transactions, REDO committed ones.

Needs old_value in log for undo.
Checkpointing
Problem: On recovery, searching the entire log from the beginning is very slow.

Solution — Checkpoint: Periodically save a checkpoint to disk. On recovery, only transactions after the last checkpoint need to be processed.

Two lists during recovery: REDO list (has [commit]) and UNDO list (has [start] but no [commit]).
