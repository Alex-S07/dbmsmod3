01 · Database Anomalies

Redundancy & Anomalies

🗃️ What is Redundancy?

Data redundancy is when the same data is stored in more than one place. Two kinds exist:

  • Row-level redundancy — entire rows are duplicated. Fix: make a column the Primary Key.
  • Column-level redundancy — derived / repeated values across columns. Leads to the 3 anomalies below.

➕ Insertion Anomaly

You can't insert new data without including other (often unrelated) data.

Example: Can't add a new student "Jerry" with Dept_ID 6 because no department 6 exists yet in the Department table.

🧠 Memory: "Can't add a child without a parent"

✏️ Update Anomaly

Duplicated data is updated in one place but not all, leaving inconsistent data.

Example: English Dept_ID is changed to 8 in the Department table, but still shows as the old ID in the Student table.

🧠 Memory: "One copy updated, others forgotten"

🗑️ Deletion Anomaly

Deleting one record unintentionally destroys other needed data.

Example: Deleting the Computer Science department also wipes out all CS students.

🧠 Memory: "Delete one thing, lose many things"

02 · Functional Dependencies

Functional Dependencies (FD)

📖 Definition

A Functional Dependency X → Y means: knowing the value of X uniquely determines the value of Y.

  • X is the determinant (left-hand side)
  • Y is the dependent (right-hand side)
If two tuples have the same X value, they must have the same Y value.

✅ Valid FD Examples

FDWhy Valid?
adm_no → {name, dept_name, dept_building}Each admission number uniquely identifies one student's info
dept_name → dept_buildingEach department name maps to exactly one building
Ssn → EnameSSN uniquely identifies an employee name
{Ssn, Pnumber} → HoursCombination determines hours worked on a project

❌ Invalid FD Examples

FDWhy Invalid?
name → dept_nameTwo students can have same name but different departments (xyz=xyz, but CS≠IT)
dept_building → dept_nameMultiple departments can share one building (B2 has both EC and ME)
name → adm_noTwo students can share a name but have different admission numbers

03 · Inference Rules

Armstrong's Axioms

Developed by William W. Armstrong (1974). These rules let you derive new FDs from existing ones.

Rule 1

Reflexivity

If Y is a subset of X, then X → Y always holds.

{roll_no, name} → name  ✓   (name is a subset of {roll_no, name})
Rule 2

Augmentation

If X → Y is valid, then adding the same attribute Z to both sides keeps it valid: XZ → YZ.

If {roll_no, name} → dept_building, then {roll_no, name, dept_name} → {dept_building, dept_name}  ✓
Rule 3

Transitivity

If X → Y and Y → Z, then X → Z (chain rule).

roll_no → dept_name && dept_name → dept_building ⟹ roll_no → dept_building  ✓
💡 These 3 axioms are sound (never produce wrong FDs) and complete (can derive all valid FDs).
🏷️
04 · FD Classification

Types of Functional Dependencies

Trivial

Trivial FD

The dependent (Y) is a subset of the determinant (X). Always true — trivially.

{roll_no, name} → name
roll_no → roll_no
Non-Trivial

Non-Trivial FD

Y is NOT a subset of X. These carry real information.

roll_no → name
{roll_no, name} → age
Multivalued

Multivalued FD

a → {b, c} where b and c are independent of each other.

roll_no → {name, age}
(name and age don't depend on each other)
Transitive

Transitive FD

Indirect dependency: a → b and b → c, so a → c indirectly.

enrol_no → dept
dept → building_no
∴ enrol_no → building_no

05 · Normalization Overview

What is Normalization?

📖 Core Idea

Normalization is the process of organizing a database to reduce redundancy and avoid anomalies by splitting large tables into smaller, well-structured ones linked by relationships.

Proposed by Edgar Codd (1NF, 2NF, 3NF). BCNF developed with Raymond F. Boyce.

1NF

No multi-valued attributes · All values are atomic · Primary key exists

Eliminate repeating groups

2NF

In 1NF + No partial dependencies (non-prime attributes must depend on the FULL primary key)

Eliminate partial dependencies

3NF

In 2NF + No transitive dependencies (NPA → NPA not allowed)

Eliminate transitive dependencies

BCNF

In 3NF + For every FD X → Y, X must be a SUPER KEY

Stricter than 3NF — eliminates remaining anomalies

1️⃣
06 · First Normal Form

1NF — First Normal Form

Rules to achieve 1NF

  • Each column must have atomic (single, indivisible) values
  • No multi-valued attributes (no lists in a cell)
  • A primary key must exist
  • Each record must be unique

3 Methods to Fix a Violation

MethodHowNotes
Method 1 ⭐ (Best)Move multi-valued attribute to a separate table, carry primary keyDEPTS + DEPT_LOCATIONS
Method 2Expand the key — create one row per valueCan cause row redundancy
Method 3Create separate columns for each possible value (Dlocations1, Dlocations2…)Wastes space with NULLs
2️⃣
07 · Second Normal Form

2NF — Second Normal Form

Key Definitions

  • Prime attribute — part of the primary key
  • Non-prime attribute — NOT part of the primary key
  • Partial dependency — a non-prime attribute depends on only part of a composite key (NOT allowed in 2NF)

Example: Student_Project Table

Primary key: {Stu_ID, Proj_ID}

Problem: Stu_Name depends only on Stu_ID (partial), Proj_Name depends only on Proj_ID (partial).

⚠️ Partial dependency exists → NOT in 2NF

Fix: Decompose into three tables:

  • Student(Stu_ID, Stu_Name)
  • Project(Proj_ID, Proj_Name)
  • Student_Project(Stu_ID, Proj_ID, Hours) — only the composite key attribute stays
3️⃣
08 · Third Normal Form

3NF — Third Normal Form

Two Equivalent Definitions

Definition 1: In 2NF + no transitive dependency between non-prime attributes (NPA → NPA is forbidden).

Definition 2: For every non-trivial FD X → Y, either:

  • X is a super key, OR
  • Y is a prime attribute

Classic Example — Student Table

FDs: rollno → game, rollno → feestructure, game → feestructure

⚠️ game → feestructure is a transitive dependency (NPA → NPA) → NOT in 3NF

Fix rule: If X→Y is a transitive dependency, split into R1(X⁺) and R2(R − Y⁺).

  • R1: (game, feestructure)
  • R2: (rollno, game)

Another Example — STUDENT Table

FDs: STUD_NO → STUD_STATE, STUD_STATE → STUD_COUNTRY

So STUD_COUNTRY is transitively dependent on STUD_NO. Solution:

  • STUDENT(STUD_NO, STUD_NAME, STUD_STATE, STUD_AGE)
  • STATE_COUNTRY(STUD_STATE, STUD_COUNTRY)
🏆
09 · Boyce-Codd Normal Form

BCNF

The Single Rule

For every non-trivial FD X → Y, X must be a super key.

BCNF is stricter than 3NF. 3NF allows Y to be a prime attribute; BCNF does NOT.

Classic BCNF Violation Example

Table: (student_id, subject, professor)

Rules: One professor teaches one subject. One subject can have multiple professors.

FDs: {student_id, subject} → professor and professor → subject

⚠️ professor → subject, but "professor" is NOT a super key → Violates BCNF

Fix: Decompose into:

  • Student(student_id, professor_id)
  • Professor(professor_id, subject)

3NF vs BCNF — Key Difference

Property3NFBCNF
Eliminates transitive depsYesYes
X must be superkey for every FDNo (Y can be prime)Yes — always
StrictnessLess strictMore strict
Always lossless decompositionYesNot always

10 · Transaction Processing

Transactions

What is a Transaction?

An atomic unit of work in a DBMS — either ALL operations complete successfully, or NONE of them take effect.

Operations include: read, write, insert, delete, update.

Low-Level Transaction Operations

OperationWhat it does
begin_transactionMarks the start of a transaction
read_item(X)Reads value of X from database into main memory buffer
modify_item(X)Changes the value in main memory buffer
write_item(X)Writes modified value from buffer back to database
end_transactionMarks end of transaction
commitTransaction succeeded — changes permanently recorded
rollbackTransaction failed — all temporary changes are undone

11 · ACID Properties

ACID Properties

A

Atomicity

All or nothing — the entire transaction completes or none of it does. Also called the "All or Nothing rule".

Abort: changes not visible. Commit: changes visible.

C

Consistency

Database must remain in a valid state before and after the transaction. Integrity constraints are maintained.

Total before = Total after (e.g. 500+200=700 before, 400+300=700 after)

I

Isolation

Concurrent transactions execute as if they were serial. Intermediate results hidden from other transactions.

Changes only visible after commit.

D

Durability

Once committed, data remains permanently — even after system crash or restart. Uses mirrored disks / backups.

12 · Concurrency Problems

Why Concurrency Control Is Needed

When multiple transactions run concurrently without control, 4 problems can arise:

1. Lost Update Problem

T1 and T2 both read X=100. T1 computes X-50=50, T2 computes X+10=110. T2 writes 110 last — T1's update ($50) is lost.

2. Dirty Read (Temporary Update)

T1 writes X=50 (uncommitted). T2 reads X=50. T1 then fails and rolls back — T2 used invalid data.

3. Incorrect Summary

T2 calculates SUM while T1 is updating records. T2 reads some old values and some new, producing a wrong aggregate.

4. Unrepeatable Read

T2 reads X=100. T1 changes X to 200. T2 reads X again and gets 200 — a different value within the same transaction.

13 · Schedules & Serializability

Schedules

Types of Schedules

TypeDescriptionProperty
SerialTransactions execute one after another (no interleaving)Always consistent
Non-SerialOperations of multiple transactions are interleavedMay cause concurrency issues
SerializableProduces same result as some serial scheduleConsistent if serializable

Conflict Serializability

Two operations conflict if they belong to different transactions, access the same item, and at least one is a WRITE.

Op 1Op 2Conflict?
Read(X)Read(X)No
Read(X)Write(X)Yes
Write(X)Read(X)Yes
Write(X)Write(X)Yes

Conflict Serializable = can be transformed into a serial schedule by swapping non-conflicting operations.

🔍 Precedence Graph Algorithm

  1. Create one node per transaction (T1, T2, …)
  2. For each conflicting pair: draw edge Ti → Tj if Ti's operation comes BEFORE Tj's conflicting operation
  3. If NO cycle → schedule IS conflict serializable
  4. If CYCLE exists → NOT conflict serializable
Serial order = topological ordering of the precedence graph

View Serializability — 3 Conditions

  1. Initial Read: If Ti reads X first in S1, Ti must read X first in S2 too
  2. Updated Read: If Ti reads X written by Tj in S1, same must hold in S2
  3. Final Write: The last writer of each item must be the same in both schedules
If conflict serializable → always view serializable. But not vice versa.

Recoverability of Schedules

TypeDescription
RecoverableTj commits only AFTER Ti commits (if Tj read data written by Ti)
Non-RecoverableTj commits BEFORE Ti — if Ti fails, Tj can't be undone (already committed)
Cascading RollbackOne transaction failure cascades to rollback multiple transactions
CascadelessTj reads only COMMITTED values (commit of Ti before read by Tj)
StrictTj can't read OR write X until the last writer of X has committed/aborted

14 · Locking Protocols

Locking & Two-Phase Locking

Types of Locks

LockAlso CalledPermission
Shared Lock (S)Read-only lockRead only. Multiple transactions can hold S-lock simultaneously.
Exclusive Lock (X)Write lockRead and Write. Only ONE transaction at a time.

Lock Compatibility Matrix

Request ↓ \ Held →SXNone
SCompatibleIncompatibleCompatible
XIncompatibleIncompatibleCompatible

Two-Phase Locking (2PL)

📈 Growing Phase

Transaction acquires (locks) all needed locks. It may NOT release any lock yet.

Ends at the lock point — when all locks have been acquired.

📉 Shrinking Phase

Transaction releases locks. It may NOT acquire any NEW lock.

Starts as soon as the first lock is released.

🔑 KEY RULE: Once you UNLOCK, you can NEVER acquire a new lock. If a lock is acquired after an unlock → NOT 2PL!

Variants of 2PL

TypeRuleBenefit
Basic 2PLGrowing + Shrinking phasesEnsures serializability
Strict 2PLHold all X-locks until commit/abortRecoverable + Cascadeless
Rigorous 2PLHold ALL locks (S and X) until commit/abortStrictest — also recoverable + cascadeless
⚠️ Disadvantages of 2PL: Deadlocks, Cascading Rollbacks, Irrecoverable schedules possible (basic 2PL)

15 · Recovery & Logging

Recovery & System Log

Types of Failures

  • System crash — hardware/software/network error
  • Transaction error — overflow, division by zero, bad parameters, logic errors
  • Local exception — e.g. insufficient bank balance
  • Disk failure — read/write malfunction or head crash
  • Physical disaster — power failure, fire, sabotage

The System Log

A sequential, append-only file on stable storage that records every database operation before it happens.

Log RecordMeaning
[start_transaction, T]Transaction T has started
[read_item, T, X]T read item X
[write_item, T, X, old, new]T changed X from old_value to new_value
[commit, T]T completed successfully — changes are permanent
[abort, T]T was aborted
Before modifying the DB, the log record is written first (Write-Ahead Logging).

Commit Point

A transaction reaches its commit point when:

  • All operations have accessed the DB successfully
  • Effects have been recorded in the log
  • A [commit, T] record is written to the log

Force-writing: The log must be written to disk before committing.

On crash recovery: transactions with [start] but no [commit] are rolled back (UNDO). Committed transactions are re-applied (REDO).

Log-Based Recovery Methods

MethodWhen DB is modifiedRecovery
Deferred ModificationOnly on commit (no writes before commit)Only REDO needed
Immediate ModificationDuring transaction (before commit)Both UNDO and REDO needed

Checkpointing

Periodic snapshots that reduce the amount of log to scan during recovery. The system writes a checkpoint record and forces all modified buffers to disk.

  • REDO list — transactions that committed after last checkpoint → redo their writes
  • UNDO list — transactions that had [start] but no [commit] → rollback

🧠 Quick Exam Review — Click to Reveal Answers

1. What are the 3 types of database anomalies?
Insertion Anomaly (can't add data without other data), Update Anomaly (inconsistent updates), Deletion Anomaly (losing unrelated data when deleting)
2. State Armstrong's 3 axioms with examples.
Reflexivity: {A,B}→B. Augmentation: If A→B then AC→BC. Transitivity: If A→B and B→C then A→C.
3. What is the difference between 3NF and BCNF?
In 3NF, for every non-trivial FD X→Y, either X is a superkey OR Y is a prime attribute. In BCNF, X must ALWAYS be a superkey — Y cannot be prime unless X is also a superkey. BCNF is stricter.
4. What are the 4 ACID properties?
Atomicity (all or nothing), Consistency (valid state before and after), Isolation (transactions don't interfere), Durability (committed data persists even after crash).
5. Explain the Lost Update Problem with an example.
T1 and T2 both read X=100. T1 subtracts 50 → 50. T2 adds 10 → 110. T2 writes 110 last. T1's write is lost. Final value should be 60 but is 110.
6. What is the rule for 2PL? How do you check if a schedule follows 2PL?
Find the first UNLOCK in each transaction. After that point, no new LOCK should be acquired. If a lock appears after an unlock → NOT 2PL.
7. What is a cascadeless schedule?
A schedule where every transaction reads only values written by COMMITTED transactions (Tj can only read X after Ti who wrote X has committed). Prevents cascading rollbacks.
8. How do you check if a schedule is conflict serializable?
Draw a precedence graph. Add an edge Ti→Tj whenever Ti's operation conflicts with and comes before Tj's (R/W, W/R, or W/W on same item). If no cycle → conflict serializable. If cycle → not serializable.
9. What is partial dependency? Give an example.
When a non-prime attribute depends on only PART of a composite primary key. Example: In Student_Project(Stu_ID, Proj_ID, Stu_Name, Proj_Name), Stu_Name depends only on Stu_ID (partial key) — not on the full key {Stu_ID, Proj_ID}.
10. What is the Dirty Read problem?
T1 writes X=50 (uncommitted). T2 reads X=50 (dirty/uncommitted value). T1 then fails and rolls back X to 100. T2 used an invalid value that no longer exists in the database.
